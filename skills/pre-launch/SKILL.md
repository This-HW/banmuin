# Pre-launch (런칭기 지원)

## 역할
사업이 `운영중`이 되기 전까지의 구간을 담당한다. 오케스트레이터가
`businesses/<slug>/knowledge/00_사업개요.md`의 `사업 단계`를 읽고 이 스킬을 호출한다.
시장조사(customer-research)와 콘텐츠 제작(content) 스킬에 작업을 위임하고,
대기리스트·베타테스터·전환 체크리스트는 직접 관리한다.

## 입력
- 사업 슬러그: `business` (기본값 `main`)
- 현재 사업 단계 (`아이디어` / `준비중` / `사전예약중`)
- 대표 지시 (전환 승인 등)

## 단계별 파이프라인

| 사업 단계 | 파이프라인 | 담당 |
|---|---|---|
| `아이디어` | 시장조사만: 수요 검증 리포트, 고객 인터뷰 질문지 10개, 합격선 판정 | pre-launch (customer-research에 조사 위임) |
| `준비중` | 시장조사 + 빌드인퍼블릭 콘텐츠 주 3회 + 랜딩 페이지 카피 초안 | pre-launch · content |
| `사전예약중` | 사전예약 유도 콘텐츠 + 대기리스트 관리 + 베타테스터 모집 + 얼리버드 혜택 운영 | pre-launch · content |
| `운영중` | 이 스킬을 호출하지 않는다. 기존 파이프라인 (수집→분석→제작→검수→발행→보고) | orchestrator |

## 홍보·팬 만들기 (전 단계 공통)

런칭기에서 가장 중요한 것은 **런칭일에 팔 대상(팬·대기리스트)을 확보하는 것**이다.
홍보 엔진은 운영중의 콘텐츠 파이프라인(기획→초안→품질 게이트→발행→분석)과 **동일한 기계**를 쓴다.
새 엔진을 만들지 않는다. 목표만 다르다: 매출이 아니라 **팬 확보와 대기리스트 전환**.

### 콘텐츠 3축 (content 스킬에 위임, 품질 게이트 동일 적용)
1. **빌드인퍼블릭** — 과정 공개 (오늘 만든 것 / 막힌 것 / 배운 것). 팔로워가 여정에 동참하게 만든다.
2. **전문성 콘텐츠** — 타깃의 고민을 해결하는 정보·노하우. 제품이 없어도 팬을 만드는 축.
   근거는 지식파일(03_고객페르소나의 고민, 09_경쟁사의 빈틈)에서만 가져온다.
3. **티저·사전예약 유도** — 출시 임박 알림, 얼리버드 혜택 안내. CTA는 단계에 맞게
   (`준비중`=팔로우·관심 유도, `사전예약중`=사전예약 신청).

### 퍼널
콘텐츠 → 프로필/랜딩 → 대기리스트 등록. 주간 리포트에 팬 증가 수와
콘텐츠→대기리스트 전환율을 기록한다. 지표의 정본은 `08_승인기준.md`의 런칭기 임계값이다.

## 출력 (산출물 경로)
- `businesses/<slug>/reports/research/YYYY-MM-DD.md` — 수요 검증 리포트 (`아이디어`, SPEC 1.7)
- `businesses/<slug>/reports/launch_readiness.md` — Go/No-Go 판정 누적 기록 (`아이디어`, SPEC 1.7)
- `businesses/<slug>/reports/research/interview_questions.md` — 고객 인터뷰 질문지 10개 (`아이디어`)
- `businesses/<slug>/drafts/YYYY-MM-DD/` — 빌드인퍼블릭·사전예약 유도 콘텐츠 초안 (content 스킬 경유)
- `businesses/<slug>/drafts/landing_copy.md` — 랜딩 페이지 카피 (`준비중` 초안 → `사전예약중` 확정)
- `businesses/<slug>/state/waitlist.jsonl` — 대기리스트 (`사전예약중`)
- `businesses/<slug>/reports/launch/YYYY-MM-DD.md` — 전환 체크리스트 판정 기록

## `아이디어` — 수요 검증

아이템이 팔릴지 검증하는 단계. 콘텐츠 제작·광고는 하지 않는다.

### 1. 수요 검증 리포트 형식
`businesses/<slug>/reports/research/YYYY-MM-DD.md` (SPEC 1.7):
아래 검증 포맷으로 작성한다. `아이디어` 단계에서는 이 파일이 수요 검증 리포트를 겸한다.
```
# 수요 검증 리포트 (YYYY-MM-DD)
## 문제 정의 (한 문장)
## 가설 (검증하려는 것 3개 이내)
## 조사 방법 (인터뷰 n명 / 커뮤니티 관찰 / 검색 수요 확인 등)
## 인터뷰 결과 요약 (응답자 수, 핵심 발언 요지 — 원문 긴 인용 금지)
## 정량 지표 vs 합격선 (표)
## 판정: 합격 / 보류 / 폐기
## 다음 액션
```
- 사실 / 가설 / 추가 확인사항을 분리 표기한다 (customer-research 스킬 규칙과 동일).

### 2. 고객 인터뷰 질문지 10개 템플릿
`businesses/<slug>/reports/research/interview_questions.md`에 사업에 맞게 각색해 저장한다.
솔루션을 묻기 전에 문제를 먼저 확인하고, 가정이 아닌 과거 행동을 묻는다.
1. (문제 상황) 이 문제를 마지막으로 겪은 게 언제인가요?
2. (현재 행동) 그때 어떻게 해결하셨나요?
3. (불편) 그 방법에서 가장 불편했던 점은 뭔가요?
4. (지불 행동) 해결을 위해 돈이나 시간을 써본 적 있나요? 얼마나 썼나요?
5. (대안) 지금 쓰고 있는 대안(경쟁사 제품·자작 방법)이 있나요?
6. (대안의 한계) 그 대안에서 가장 아쉬운 점은 뭔가요?
7. (솔루션 반응) 이런 게 있다면 써보시겠어요? (솔루션 설명 후)
8. (가격 탐색) 얼마 정도면 지불 의사가 있으신가요?
9. (확산) 주변에 같은 문제를 겪는 분이 있나요?
10. (베타 전환) 출시되면 먼저 써보고 피드백을 주실 수 있나요?

### 3. 합격선 (임계값)
- `businesses/<slug>/knowledge/08_승인기준.md`에 `## 런칭기 임계값` 섹션이 있으면 그 값을 정본으로 사용한다.
- 섹션이 없으면 아래 기본값을 사용한다 (기본값 사용 시 리포트에 "기본값 적용" 표기):
  | 지표 | 합격 | 보류 | 폐기 |
  |---|---|---|---|
  | 핵심 문제 공감 ("이 문제를 겪어봤다", 응답자 중) | 60% 이상 | 40–60% | 40% 미만 |
  | 유료 전환 의사 ("돈 내고 쓰겠다", 응답자 중) | 30% 이상 | 15–30% | 15% 미만 |
- 대기리스트 알림 임계값 기본값: 100명 (도달 시 대표에게 알림)
- `보류` 판정 시: 가설을 바꿔(피벗) 재검증하거나, 표본을 늘려(최소 10명) 재측정한다.
- `폐기` 판정 시: 리포트에 사유를 기록하고 루틴을 중단, 대표에게 알린다.

### 4. Go/No-Go 누적 기록
- 수요 검증 리포트를 쓸 때마다 `businesses/<slug>/reports/launch_readiness.md`에 한 줄씩 누적한다
  (날짜 | 판정: Go/No-Go/보류 | 근거 한 줄). 아이디어 단계의 최종 산출물은 이 파일이다.
- `폐기`가 누적 2회면 아이템 재검토를 대표에게 요청한다 (에이전트가 임의로 폐기 선언하지 않는다).

## `준비중` — 출시 준비

### 1. 빌드인퍼블릭 콘텐츠 (주 3회, content 스킬에 위임)
- pre-launch가 주제를 선정 → content 스킬에 "목표 한 줄"로 전달 →
  content 파이프라인(기획→초안→품질 게이트)은 그대로 적용한다.
- 주 3회. 요일 배분은 `businesses/<slug>/content_calendar.md`에 기록한다.
- 과정 공개형 주제 10선 (사업에 맞게 각색):
  1. 왜 이 아이템을 시작했는지
  2. 오늘 만든 것 / 오늘 배운 것
  3. 고객 인터뷰에서 들은 한 마디 (익명화)
  4. 실패담 (잘못 판단했던 것)
  5. 숫자 공개 (쓴 비용·쓴 시간 — 확인된 것만)
  6. 다음 마일스톤과 현재 진척
  7. 쓰고 있는 도구·방법 공유
  8. 팔로워에게 질문 던지기
  9. 비하인드 (작업 환경·하루 루틴)
  10. 출시 D-day 카운트
- 규칙: 미완성·과정의 공개는 허용한다. 허위 과장(미출시 기능을 출시된 것처럼,
  미확정 숫자를 확정인 것처럼)은 금지한다. 숫자와 일정은 확인된 것만 쓴다.

### 2. 랜딩 페이지 카피 초안
`businesses/<slug>/drafts/landing_copy.md`에 초안을 작성한다.
구조는 아래 `사전예약중`의 랜딩 카피 구조를 따르되, CTA 부분은
"사전예약 수단 확정 후 기재"로 비워둔다.

## `사전예약중` — 사전예약 모집

### 1. 사전예약 유도 콘텐츠 (content 스킬에 위임)
- 빌드인퍼블릭과 동일한 위임 방식. 톤은 content 스킬의 `사전예약중` 노트를 따른다
  (예약 유도 CTA 포함).
- 빈도는 `businesses/<slug>/content_calendar.md`의 예약 유도 분량을 따른다.

### 2. 대기리스트 관리
- 파일: `businesses/<slug>/state/waitlist.jsonl` (JSON Lines, 1줄 1건)
- 스키마 (SPEC 1.7이 정본):
  ```json
  {"id":"wl_20260930_001","joined_at":"2026-09-30T10:00:00+09:00",
   "name":"...","contact":"...","source":"landing",
   "status":"waiting","early_bird":true,"beta":false,"notes":""}
  ```
  - `source`: landing | threads | blog | youtube | referral | 기타
  - `status`: `waiting` → `invited` → `converted` | `churned` (역방향 전이 금지)
  - `early_bird`/`beta`: 얼리버드 대상·베타테스터 여부
- 핵심 규칙:
  - 신청 접수 시 중복 확인 (`contact` 기준). 중복이면 새 줄을 추가하지 않고 기존 건의 `notes`에 추기한다.
  - `id`는 `wl_YYYYMMDD_일련번호` 형식으로 발급한다.
  - 대기리스트는 `state/`에 저장한다 (지식파일이 아니다). 개인정보를 포함하므로
    절대 Git에 커밋하지 않는다 (`.gitignore`의 `**/state/waitlist.jsonl` 규칙).
    공개 리포지토리 운영 시 SPEC 3.4의 공개/비공개 구분을 따른다.

### 3. 랜딩 카피 구조 (확정본)
`businesses/<slug>/drafts/landing_copy.md`를 아래 구조로 확정한다.
모든 주장은 지식파일 근거를 대조한다 (content 스킬 규칙 6과 동일).
- **헤드라인**: 한 줄 가치 제안 (`00_사업개요.md`의 한줄 소개 기반)
- **고민 공감**: `03_고객페르소나.md`의 고민을 인용 (특정 개인이 식별되지 않게 익명화)
- **솔루션**: `01_상품서비스.md` 기반. 출시 전이므로 "출시 예정"으로 표기하고,
  출시된 것처럼 쓰지 않는다.
- **사전예약 CTA**: 얼리버드 혜택 + 신청 방법 (대기리스트 등록 경로) + 모집 수량·기간 상한 명시

### 4. 베타테스터 모집 절차
1. 모집 조건 정의: 대상, 인원 상한 (08_승인기준.md의 런칭기 임계값 또는 대표 지정)
2. 모집 콘텐츠 제작 (content 스킬에 위임)
3. 신청 접수 → `waitlist.jsonl`에 `status=waiting`으로 기록
4. 선정 기준 적용 (예: 타깃 페르소나 부합도, 피드백 제공 가능 여부) → `converted` / `waiting` 유지
5. 피드백 수집: 수집 항목을 사전에 정의한다 (사용 시나리오, 불편 지점, 지불 의사 변화)
6. 베타 종료 후 피드백 요약을 `reports/launch/`에 기록 → `운영중` 전환 판단의 입력으로 사용

### 5. 얼리버드 혜택 설계
- 혜택 유형과 조건을 문서로 정의한다 (`drafts/earlybird.md`):
  - 유형: 가격 할인 / 한정 구성 / 평생 혜택 등 (사업에 맞게 1가지만 선택 권장)
  - 조건: 사전예약자 한정, 수량 상한, 기간 상한
- `02_가격정책.md`의 할인 조건과 정합해야 한다. 어긋나면 대표 승인을 받아 02를 먼저 수정한다.
- 허위 희소성(실제로는 무제한인데 "선착순" 표기)은 금지한다.

## `운영중` 전환 체크리스트

### 전환 조건
| 전환 | 조건 (모두 충족) |
|---|---|
| `아이디어` → `준비중` | 수요 검증 리포트 판정 `합격` |
| `준비중` → `사전예약중` | 랜딩 카피 초안 완성 + 사전예약 접수 수단(폼·링크 등) 준비 완료 |
| `사전예약중` → `운영중` | 상품·서비스 출시 가능 상태 + `01_상품서비스.md`·`02_가격정책.md` 확정 + 대기리스트 `converted` 건 존재 + 팬 목표(08_승인기준.md) 달성 |

### 전환 절차 (대표 승인 필수)
1. pre-launch가 조건 충족 여부를 `businesses/<slug>/reports/launch/YYYY-MM-DD.md`에 기록한다.
2. 오케스트레이터 경유로 대표에게 전환 요청을 알린다 (텔레그램).
3. **대표의 명시적 승인**이 떨어지면 `businesses/<slug>/knowledge/00_사업개요.md`의
   `사업 단계` 값을 변경한다.
4. 변경 일시·승인 근거를 `reports/launch/` 기록에 남긴다.
5. 승인 없이 에이전트가 임의로 단계를 변경하는 것은 금지한다.

## 핵심 규칙
1. **사업 단계 변경은 대표의 명시적 승인 없이 하지 않는다.** (위의 전환 절차 준수)
2. **없는 수요를 지어내지 않는다.** 인터뷰 응답자 수·전환율 등 수치는 실제 측정값만 사용한다.
